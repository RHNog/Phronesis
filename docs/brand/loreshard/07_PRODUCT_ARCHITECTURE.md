# Proposed product architecture

This is a future naming architecture, not authorization to change current Phronesis code, UI, routes, packages, repositories, or deployments.

## Recommended initial suite

> **Scan. Market. Buylist. Vault. Ledger.**

| Proposed module | Role |
|---|---|
| **LoreShard Scan** | Scanner intake, image recognition, card identification, and sealed-product recognition |
| **LoreShard Market** | Pricing, comps, liquidity, sales velocity, demand, spread, market depth, and market signals |
| **LoreShard Buylist** | Vendor buying, offer calculation, bulk intake, and event workflows |
| **LoreShard Vault** | Inventory, collection management, sealed product, provenance, and valuation |
| **LoreShard Ledger** | Cost basis, purchase history, margins, sales history, and realized performance |
| **LoreShard API** | Developer/data integrations, marketplace tools, and internal automation |

## Possible later products or branded outputs

- LoreShard Vision
- LoreShard Index
- LoreShard Confidence
- LoreShard Consensus
- LoreShard Signals

These names remain conceptual and require product, legal, and architecture review. A branded output should identify LoreShard as its source; it must not turn “shard” into the generic name for an input or record.

## Architecture principles

1. The master brand stays consistent across modules.
2. Module names describe user outcomes in ordinary language.
3. Generic internal objects remain signals, observations, evidence, listings, sales, and inventory—not shards.
4. The suite must accommodate additional collectible and physical-asset categories.
5. Any transition from existing Phronesis module labels occurs only through the Gate 4 migration plan.
